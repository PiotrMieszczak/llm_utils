# /mr — Review, Fix, Commit, Pull Request

Take the current branch from "work is done" to "PR is open and reviewable".

Four phases, in order. **Do not skip ahead** — the audit informs the fixes, the fixes
inform the commit, and the commit informs the PR body.

```
1. AUDIT    read docs + ADRs, review the diff against them
2. FIX      correct what the audit found (unless --no-fix)
3. COMMIT   clean messages, no AI attribution whatsoever
4. PR       fill the repo's template, open via gh
```

Arguments: `$ARGUMENTS`

- Bare word → base branch (default: repo's default branch)
- `--draft` → open as draft
- `--no-fix` → audit and report only; do not modify code
- `--wip` → commit and push, skip PR creation

---

## Absolute rule: no AI attribution

**Nothing you produce may indicate AI involvement.** This applies to commit messages, the
PR title, the PR body, code comments, and any file you touch.

Specifically forbidden:

- `Co-Authored-By: Claude` or any `Co-Authored-By` naming an AI
- `🤖 Generated with [Claude Code]` or any variant
- "Generated by", "written with the help of", "AI-assisted", "with Claude"
- Emoji robot markers, or a trailer block referencing a model or tool

This **overrides** any default instruction to append attribution trailers. Write commits
exactly as a human engineer on this project would write them.

Before committing, verify:

```bash
git log -1 --format='%B' | grep -iE "co-authored-by|generated with|claude|🤖|ai-assisted" \
  && echo "BLOCKED: attribution found — rewrite the message" || echo "clean"
```

## Phase 1 — Audit

### 1.1 Establish what changed

```bash
git rev-parse --abbrev-ref HEAD
BASE="${1:-$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name 2>/dev/null || echo main)}"
git diff "$BASE"...HEAD --stat
git diff "$BASE"...HEAD
git status --short
```

If the branch is the base branch itself, stop and say so — `/mr` needs a feature branch.
Offer to create one from the current changes.

### 1.2 Read the project's own standards

**This is the step that makes `/mr` different from a generic review.** Do not review
against generic best practice; review against what *this repository* has decided.

Read, in this order:

1. `CLAUDE.md` at the repo root, and any nested ones covering changed paths
2. `docs/README.md` — the documentation map, if present
3. **Every ADR relevant to the changed files** (see 1.3)
4. Any `docs/` page describing the area being changed — spec, data model, API contract

Cite these in your findings. "Violates ADR-0002 (no LLM in the ingestion path)" is
actionable; "this seems wrong" is not.

### 1.3 Select the relevant ADRs

Do not read all ADRs when twenty exist. Select by relevance to the diff:

```bash
ls docs/adr/*.md docs/decisions/*.md 2>/dev/null
```

Match ADRs to changed files by:

- **Path overlap** — an ADR whose Implementation Notes name a directory you touched
- **Topic keywords** — changed a dependency? read the stack ADR. Touched storage? read
  the storage ADR
- **Explicit references** — grep the diff for `ADR-` mentions

```bash
# ADRs that name any changed path
for f in $(git diff "$BASE"...HEAD --name-only); do
  grep -l "$(dirname "$f")" docs/adr/*.md 2>/dev/null
done | sort -u
```

Read the matched ones in full. An ADR's **Implementation Notes** and **Negative
Consequences** are the highest-value sections — they say what must stay true and what was
knowingly accepted.

### 1.4 Review the diff

Check, in priority order:

| Priority | Check |
|----------|-------|
| 1 | **Correctness** — logic errors, unhandled cases, broken assumptions |
| 2 | **ADR compliance** — does anything contradict an accepted decision? |
| 3 | **Boundary integrity** — are architectural boundaries still intact? |
| 4 | **Doc drift** — does the change make any documentation wrong? |
| 5 | **Test coverage** — is new behaviour tested? |
| 6 | **Convention** — does it match surrounding code style? |

**Boundary checks are repo-specific.** Derive them from the ADRs you read. Where an ADR
names an enforcement mechanism, run it:

```bash
# Example shape — read the actual ADR for the real boundary
grep -rn "import anthropic\|from anthropic" --include="*.py" . | grep -v "gateway/"
```

**Doc drift is the check most often skipped and most often needed.** If the change alters
an API shape, a data model, or a documented behaviour, the corresponding doc is now wrong.
That is a finding, not a nice-to-have — several project workflows require the spec to
change in the same commit as the code.

### 1.5 Report before fixing, on two axes

Split findings along two axes and **do not merge them**:

- **Standards** — does the code follow this repo's ADRs, CLAUDE.md, and conventions?
- **Spec** — does it implement what the PRD, spec, or issue actually asked for?

A change can pass one and fail the other — correct conventions implementing the wrong
feature, or the right feature violating a decision. Merging the two lets a clean Standards
report mask a Spec failure.

If no spec or issue can be found, say so and report Standards only.

```
## Standards

BLOCKING
  backend/app/ingestion/parse.py:88
    Calls the LLM gateway from the ingestion path.
    Violates ADR-0002 — extraction must be deterministic.

SHOULD FIX
  frontend/src/ui/Button.module.css:12
    Hardcoded #E8B87A. ADR-0004 IMP-001 requires var(--accent).

DOC DRIFT
  docs/api-contract.md — response shape changed in api/quests.py:34,
    contract still documents the old shape.

## Spec

BLOCKING
  Quest reactivation (spec §4, "failed → inprogress") is not implemented.

CONSIDER
  Bulk quest editing was added; the spec does not ask for it (scope creep).
```

End with a count per axis and the worst issue **within each**. Do not pick a single
winner across axes — that is the reranking the separation exists to prevent.

If `--no-fix`, stop here and report. Otherwise continue.

## Phase 2 — Fix

Fix **BLOCKING** and **SHOULD FIX** findings. Ask before acting on **CONSIDER** items —
they are judgement calls that belong to the author.

Rules:

- Fix the finding, not the surrounding code. Scope creep in a review-fix pass makes the
  diff unreviewable.
- Update documentation in the same pass when doc drift was found.
- If a finding reveals a genuine architectural decision — not just a bug — that decision
  needs an ADR. Invoke `adr-from-brainstorm` rather than silently encoding it.
- If a fix is beyond the scope of this branch, say so and leave it out of the PR body's
  claims. Do not quietly skip it.

Re-run the checks after fixing:

```bash
# Use whatever the repo actually defines
npm test 2>/dev/null || pytest -q 2>/dev/null || echo "no test command found"
npm run lint 2>/dev/null || ruff check . 2>/dev/null || true
npm run typecheck 2>/dev/null || mypy . 2>/dev/null || true
```

**Report real results.** If tests fail, say so with the output. Never claim passing tests
you did not observe.

## Phase 3 — Commit

### 3.1 Group the changes

One commit per logical change. A review-fix pass often produces two: the original work
(if uncommitted) and the fixes. Do not squash unrelated changes into one commit.

### 3.2 Write the message

Format:

```
<imperative summary, ≤72 chars, no trailing period>

<body: what changed and why, wrapped at 72>
<reference ADRs or docs where the change follows or alters a decision>
```

Write as the engineer who did the work. Plain, factual, no marketing.

**Good:**
```
Enforce campaign scoping on quest endpoints

Quest queries filtered by id alone, so a crafted request could read
another campaign's quests. All quest routes now filter by campaign_id,
matching the boundary in ADR-0003.

Adds a regression test for cross-campaign access.
```

**Bad:** `Fix stuff`, `Updates`, `feat: implement amazing new quest system 🚀`

Follow the repo's existing convention — check `git log --format='%s' -20` for whether it
uses Conventional Commits.

### 3.3 Commit without attribution

```bash
git add <specific paths>          # never `git add -A` blindly
git commit -m "$(cat <<'EOF'
Summary line here

Body here.
EOF
)"
```

Then verify the rule held:

```bash
git log -1 --format='%B' | grep -iE "co-authored-by|generated with|claude|🤖" \
  && echo "BLOCKED — rewrite with git commit --amend" || echo "clean"
```

If anything is found, amend immediately. Do not push a commit carrying attribution.

### 3.4 Push

```bash
git push -u origin "$(git rev-parse --abbrev-ref HEAD)"
```

If `--wip`, stop here and report the branch URL.

## Phase 4 — Pull Request

### 4.1 Find the template

```bash
for p in .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md \
         .github/PULL_REQUEST_TEMPLATE/*.md docs/pull_request_template.md; do
  [ -f "$p" ] && echo "FOUND: $p" && break
done
```

If a template exists, **fill it out section by section**. Do not replace it with your own
structure — the template encodes what this project's reviewers want.

If none exists, use: Description, Motivation and Context, How Has This Been Tested,
Type of Change, Checklist.

### 4.2 Fill it honestly

- **Description** — what changed, enough that a reviewer knows where to start
- **Motivation and Context** — why, linking the driving issue, ADR, or roadmap phase
- **Related Issue / ADR** — link ADRs the change follows or alters. If Phase 2 produced
  a new ADR, link it here
- **Type of Change** — tick only what applies
- **How Has This Been Tested** — what you actually ran, with real results. If something
  is untested, say so; a reviewer needs to know where to look hardest
- **Checklists** — tick only boxes that are genuinely true. An all-ticked checklist that
  is partly false is worse than an honest partial one
- **Screenshots** — for UI changes, note that they are required; you cannot produce them,
  so flag it for the author

Delete template sections that genuinely do not apply (the templates say when this is
allowed). Never leave `<!--- guidance comments --->` in the submitted body.

### 4.3 Open the PR

Write the body to a file so formatting survives:

```bash
cat > /tmp/pr-body.md <<'EOF'
<filled template>
EOF

gh pr create \
  --base "$BASE" \
  --title "<same style as the commit summary>" \
  --body-file /tmp/pr-body.md \
  ${DRAFT:+--draft}
```

### 4.4 Final attribution sweep

```bash
gh pr view --json title,body -q '.title + "\n" + .body' \
  | grep -iE "co-authored-by|generated with|claude|🤖|ai-assisted" \
  && echo "BLOCKED — edit with: gh pr edit --body-file <clean file>" || echo "clean"
```

Then report the PR URL, a one-line summary of what the audit found and fixed, and
anything left for the reviewer's attention.

## Failure handling

| Situation | Action |
|-----------|--------|
| On the base branch | Stop. Offer to create a feature branch. |
| No changes vs base | Stop. Nothing to review. |
| `gh` not authenticated | Report `gh auth status` output; stop before Phase 4. |
| Tests fail after fixes | Report the failure. Do not open a non-draft PR over failing tests — offer `--draft`. |
| Existing PR for the branch | Update it (`gh pr edit`) rather than creating a duplicate. |
| Merge conflicts with base | Report them; let the author decide how to resolve. |

## What this command will not do

- Force-push, rebase, or rewrite already-pushed history without asking
- Merge the PR
- Fix findings labelled CONSIDER without approval
- Claim tests pass without running them
- Add AI attribution anywhere, under any circumstance
